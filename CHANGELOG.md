## [1.15] - 2026-10-09

### Added
- Health → Insights: weekly and monthly trends from the walks, runs and rides recorded in Wockett, the first piece of the Premium bundle Joe approved on 2026-10-08. Free, as decided on 2026-09-15 ("a user's own week is their own data"): the period's distance, compared with the same stretch of last week or month (Wednesday noon against last Wednesday noon, so a week in progress is not always "down"), a day-by-day chart, and activities, active time, estimated steps and active days. The depth that `ProFeature.advancedAnalytics` will gate: the last 8 weeks or 6 months, the walk/run/ride mix, the busiest weekday and usual time, and each pet's distance and walks. Pro gating is still off, so everyone sees all of it until the paywall ships. Weeks follow the person's calendar (Sunday in the US), sessions flagged as possible driving are left out, and the numbers come from session history, so they match Activity History and work without Health access.
- Settings → Support → **Rate Wockett**, which opens the App Store's write-a-review page for Wockett. The system rating prompt added in 1.14 only appears when iOS allows it (at most three times a year, never in TestFlight), and with four ratings on the listing, a way to rate that is always there matters. Checked with a UI test that finds the row and confirms tapping it hands the review link to the system; the simulator has no App Store, so the final hop to the review page needs a phone (on the next QA card).
- Trail regions for Florida (probe: Orlando), Alabama (Birmingham), Kentucky (Louisville), West Virginia (Charleston) and Maryland (Baltimore) in `tools/regions.json`, so `make_region.sh` can build them. All five passed the release gates on 2026-10-08 with builder 1.3.2: Florida 70,546 trails (23 MB), Alabama 24,641, Kentucky 15,293, West Virginia 15,682, Maryland 19,632.

### Fixed
- Community: likes on achievement posts and Wocketts on shared routes now count for everyone. Each is a small vote record the voter creates, counted per post or route, because CloudKit lets only a record's creator change it and every like or Wockett from anyone but the author was failing (likes silently, Wocketts with "Couldn't save your Wockett"). One vote per person per item, across their devices. A like or Wockett that fails to save is taken back on screen and says so. "Wocketts received" counts the votes on your shared routes.
- The Apple Health permission text now says what Wockett reads. It said only "Wockett reads your step count", but the app also reads walking distance, flights climbed, active calories, sleep, resting and walking heart rate, heart rate variability, and walking speed, step length and symmetry (Recovery and Walking health). App Review can reject a permission string that undersells what is accessed; the 1.14 release check flagged it. The write text now names runs as well as walks and rides. Every type listed was checked against the `readTypes` in `StepManager`, `RecoveryService` and `GaitHealthView`; the text makes no privacy claim, since joining a community challenge uploads your step totals.
- The privacy manifest now says what Community collects. Shared routes (their full GPS line), achievement posts, challenges and challenge entries (step totals, some read from HealthKit) are written to the CloudKit public database, which the developer can read, and each record carries the generated nickname, CloudKit's creator user record ID, and on challenge entries an app-made device ID. So Precise Location, Health and Fitness are linked to the person, and Other User Content, User ID and Device ID are collected, all for App Functionality. Tracking stays No: nothing goes to advertisers or data brokers. Found by an audit against the App Store label on 2026-10-08 (read from source); the App Store Connect label is changed to match, and its Usage Data and Diagnostics entries removed, since nothing sends either.
- Settings → Trail Regions lists each region once, at its newest version, even in the seconds a publish has two records for it.
- Community: Report on a shared route, post or challenge now opens an email to support@wockett.app naming the item, so a report reaches us and the item can be removed for everyone. Until now a report only hid the item on the reporter's own phone. Report is also on the Community hub's posts, top routes and challenges, which had none. The item is hidden for the reporter once the email is handed to a mail app; with no mail app set up, the app shows the address and a Copy Report button instead. The hub stops showing anything reported or blocked on another screen without needing a refresh. Send Feedback and reports share one address.
- Downloading a trail region no longer leaves its row stuck on "Downloading 100%…" after the pack has installed. The last progress update is delivered on a separate main-actor task, and it could run after the download finished and overwrite "installed" with "downloading". Seen on the first Development download of North Carolina v3 (2026-10-08): the pack was on disk and open, but the row never changed until the screen was reopened. A progress update now only applies while the region is still downloading. 1 new test, red without the fix.
- Trail regions: a region record whose code isn't a short lowercase code (like `nc`) is ignored, and a download checks the code again before writing anything. The code becomes the pack's file name, so only plain codes are used.
- The empty Trails list no longer says Wockett has trail data "for North Carolina so far". With South Carolina, Virginia, Tennessee and Georgia packs on the way (built and checked on 2026-10-08), someone in Atlanta with nothing downloaded would have been told their state isn't covered. It now reads "No trails within 10 miles. Download your state in Settings → Trail Regions to see its trails. More states are on the way."
- Community: Block now hides a person by their iCloud account instead of their display name. Display names are random and only 270 exist, so blocking one hid everyone who shared it, and a blocked person could get past it under another name. A block hides all of that person's posts, routes and challenges straight away, everywhere. Blocks made before this keep working, but never hide your own content, and Block is no longer offered on your own posts, routes and challenges.

### Internal
- A "Critic verdict" check fails a major PR (a `feat/` branch, or more than `criticMinLines` changed lines of Swift outside the tests) whose description records no critic verdict, or a BLOCK one. The PR template gains Critic verdict and Spec lines.
- One command builds any trail region: `bash scripts/trail-pack/make_region.sh <region>`, from a row in `tools/regions.json` (name, Geofabrik path, a probe point at the main city, bundled or not). It replaces a hand-edited copy of `build_nc.sh` per state; `build_nc.sh` now calls `make_region.sh nc`. Joe, 2026-10-08: "figure out an efficient way to add new region packs easily". After the build, `tools/region_release.py` gates the pack (builder verify, trails inside the extract's bounds, named trails within 25 km of the probe city, at least 100 trails, a 150 MB budget) and writes the release manifest: every field of the CloudKit `TrailRegionPack` record computed from the pack instead of typed (`trailCount`, `sizeBytes`, `builtAt`, `schemaVersion`), the next `packVersion`, a sha256, the extract's md5, and a what-changed diff against the last published pack. The version and the extract's md5 are stamped into the pack's own `meta`, so a file now says which release it is. `tools/pack_quality.py` reports how a pack reads in the app: named share, named trails that arrive in several pieces (grouped as the app groups them, same name within 400 m), and short unnamed clutter. On today's NC pack: 7,336 named trails, 16% of them in pieces (Neuse River Trail in 29), and 84% of rows unnamed, 38% of those under 100 m — the baseline for the curation work next. Checked: `make_region.sh nc` on the 2026-09-09 extract runs in 40 s; its bundled pack is byte-identical to the old script's command, and its full pack's 59,902 trail rows hash identically to the published `nc-full-v2`. 10 new tests; disabling the gates turned 5 red, disabling the grouping turned 1 red.
- Trail region packs publish to CloudKit by command instead of by hand in CloudKit Console: `python3 tools/region_publish.py publish <region>` uploads the newest release manifest's pack as a `TrailRegionPack` record to the Development environment, and `--production --tested` sends it to the one users get, after a device has downloaded it from Development. Every field comes from the manifest; it refuses before touching CloudKit when the pack changed since its manifest was written, the version is not newer than every record already there, or Production is asked for without `--tested`. Replacing is create-then-delete (cktool cannot edit a record in place), and nothing is removed until the new record is visible. `make_region.sh` now numbers a release from the live Production version (`region_publish.py live-version`), not a local file: on 2026-10-08 the local record said nothing was published while v2 was live. Tokens are saved once with `xcrun cktool save-token --type management|user --method file` (the Keychain method did not take). First real run: North Carolina v3 (builder 1.3.0, 34,422 trails, 12.6 MB) built and uploaded to Development; Production still v2. 9 new tests against a fake cktool; removing each safeguard turned its test red.
- `tools/region_publish.py` no longer passes `--team-id` to `cktool delete-record`, which has no such option. The first Production publish (NC v3, 2026-10-08) uploaded v3, confirmed it was visible, then failed at removing v2, so both sat in Production until v2 was deleted by hand; users kept a working pack throughout. The tests missed it because their fake `cktool` accepted any option. It now refuses anything outside each command's real option list, copied from `cktool --help` and hardcoded so it cannot agree with the code by construction. With the old `--team-id` back, 2 tests go red.
- `tools/region_publish.py` waits up to about a minute for a record it just created to show up in CloudKit before giving up. On 2026-10-08 the South Carolina v1 upload stopped with "not visible" although the record was there a minute later; CloudKit's query index lags a create. The safety rule is unchanged: nothing older is removed until the new record is seen. 1 new test with a fake that lags like CloudKit; without the wait it goes red, and the not-visible test now also checks the whole wait happened.
- "Critic verdict" is now a required check on `main`, after it posted on a PR and failed a deliberate break.
- A region pack must now cover most of its state to ship: `region_release.py` fails the release when fewer than 50% of the state's cities and towns (`place=city,town`, exported by `make_region.sh`) have a named, walkable trail of at least a quarter mile, judged on the whole trail, within 3 miles. Joe, 2026-10-08: "If we can't deliver useful trails, we should hold off adding more." With builder 1.4.0 the ten published states measure Maryland 96%, Florida 87%, Virginia 84%, West Virginia 74%, North Carolina 73%, Georgia 70%, Alabama 61%, South Carolina 58%, Tennessee 58%, Kentucky 51%. The figure and the first towns without a trail print on every build. 4 new tests; removing the walkable check, the whole-trail length, or the gate itself turned its test red.
- Trail regions have written standards, `scripts/trail-pack/STANDARDS.md`, and the tools to hold each update to the last (Joe, 2026-10-09: the logic should improve with each update):
  - No coverage regression: a new version of a state may not cover more than 2 points fewer towns than the published one, unless shipped with `ACCEPT_REGRESSION="<why>"`, which is recorded.
  - Every build prints what to review before the next builder rule: one name on many separate trails (descriptions, name variants) and very long single "trails" (a place name painted on every way).
  - The published record keeps an archived copy of exactly what users have (`published/<region>-v<N>.wktpack`) and a history of each version's builder and coverage. Until now it pointed at the build folder's pack, which the next build overwrites, so "what changed against the published version" compared a new pack with itself. The ten live states were archived and their coverage recorded as the baseline on 2026-10-09 (each archive checked against the published sha256).
  - 5 new tests; removing the regression gate, the archive, the archive clean-up, or either review list turned its test red.
- Documented that only the `TrailPublisher` security role can create trail region packs in CloudKit, and that `cktool` runs as the developer, so it can't show whether a role blocks anyone.
- One Claude worktree per branch (`~/Desktop/Apps/Wockett-claude/<branch>`), so several sessions can work on Wockett at once.
- Tests: the vote deadline tests no longer depend on how fast the machine is. On GitHub Actions they failed twice on 2026-10-09 without anything being broken. Swift Testing starts every test at once, and on a busy runner a test can wait over a minute just to get onto the main actor. One test passed after 84 s, but its 1-minute time limit was counted from the start, so xcodebuild killed the test app and the run reported only 95 of its roughly 520 unit tests. Other runs failed the "finished in under 5 s" checks (7.7 s seen). The deadline now takes its sleep as a parameter, which defaults to `Task.sleep`, so the app's behaviour is unchanged. Each test passes the deadline when it chooses, waits for explicit signals, and caps every wait by main-actor turns rather than seconds, so a broken deadline fails instead of hanging. The time limits and the wall-clock checks are gone.

## [1.14] - 2026-10-08

### Added
- Directions to a trail inside Wockett. Joe, 2026-09-26: "we should also offer walking directions within the app before defaulting to launching the Maps app. If it's close, maybe the user will want to bike or walk to the listed trail." Until now a trail's detail had one button, which left the app for Apple Maps even when the trail was a ten-minute walk away. Now, when you are farther than the 150 m Start Walk radius, the detail shows **Get to the trail** directly under the trail's name, above its stats, so Start is on screen without scrolling (Start Walk at the trail moved up to the same place): two tiles, on foot (Walk, or Run in Run mode) and Ride, each with MapKit's time and distance to the trail's nearest point, the same point Maps was given. The chosen one is drawn on the Trails map as a dotted line in the activity's colour over a light casing, so it never reads as part of the solid green trail, and the map frames it with the trail above the panel, using the panel's measured height; it frames again when the directions make the panel taller, because a frame taken before they arrived put the route behind it. **Start Walk to Trail** (or Run, or Ride) starts an ordinary guided session to the trail, routed on streets by the session's own MKDirections legs like every other guided route. Within 150 m of the trail that session offers the trail itself — a banner, "You're at Rocky Branch Trail", with Start trail walk and Not now, a spoken line with voice cues on, and a notification when the phone is in a pocket; the offer also stays under More. It does not finish at the access point, as a two-waypoint route otherwise would. Saying yes turns the same session into the trail walk rather than ending one and starting another: one workout in Health, one entry in history, named for the trail, with the time, distance and steps from home included. The session already swaps its route in place when a loop is walked backwards, so this reuses that path (`onRouteReversed` is now `onRouteChanged`), and the 20/40/60/80% markers, the 1 km pins on the map and the distance left count from the trail, not from home. The way there's percentage splits are dropped at the switch, so the summary lists the trail's once. The Live Activity is restarted with the trail's name and a total of the way there plus the trail, because the widget shows total − covered as the distance left and covered includes the way there: with the trail's length alone, a walk there longer than the trail read 0 left from the start. The same total is used when a session is restored after a crash. The arrival notification has one fixed identifier and is withdrawn when the trail walk starts or the session ends. The trail travels with the session's route and its crash snapshot, so a session restored on the way there still offers the trail on arrival; if that part of a snapshot ever fails to decode (a later change to the trail model), the walk still restores without the offer instead of being lost. **Which option leads** depends on distance: on foot under 3 km (about 2 mi), the bike from there to 13 km (about 8 mi), and from 13 km a primary **Drive in Maps** with the two tiles below it. - The downloadable North Carolina trail pack joins unnamed paths into continuous corridors and names a sidepath after the road it runs beside (`tools/build_trail_pack.py` 1.2.0). On a walk on 2026-09-26 Joe found the paved path along NC 12 from Kitty Hawk into Duck listed as 58 separate "Unnamed Trail" rows of 30-300 m: OSM splits an unnamed path at every driveway and side street, and 1.1.0 could only chain ways that share a name. It is now three rows, all open to bikes: Ocean Boulevard Path (4.1 km), Duck Road Path (4.2 km), and Duck Road Path again (6.9 km) after the stretch through Duck village that OSM maps as sidewalk.
  - **Joining.** Unnamed ways chain where their ends meet (the same node, or within 3 m) if they are the same kind of way, and a chain never mixes paved and unpaved; boardwalks and untagged pieces are neutral. path, footway, cycleway, steps and pedestrian are one family, because one sidepath is tagged several of those ways; tracks and bridleways only join their own kind. Where three or more ways meet, the straightest pair joins, and only if it turns by 45° or less, so a sidepath runs straight past a beach access and the access stays its own row. A way that runs through the meeting point without being split there counts as two of those ways. A joined row takes the smallest member id, so ids stay stable across rebuilds, and the tags of its longest member.
  - **Crossings.** Road crossings are now kept in the extract: they are the only link between the halves of a sidepath either side of a side street (the Duck path broke at 12-18 m gaps without them). A crossing that joins nothing is dropped, including a named one, and crossings do not count toward the 30 m length floor, so a crosswalk cannot stitch two scraps into a "trail".
  - **Access on joined rows, named and unnamed.** Crossings do not vote on bike, foot or horse access, surface, difficulty or dogs. The first cut let them vote, and because a crosswalk is rarely tagged for bikes, it took bike access off the whole Duck sidepath (bicycle=designated cycleways) and 3.5 km of the Charlotte Rail Trail; cycleways marked no-bike went from 13 to 207. Among the other members, a mode is allowed when the members that allow it make up at least half the row's length (crossings excluded) and none forbids it outright (bicycle=no, or access=no without a yes for that mode). A member that says nothing, such as an untagged footway in a cycleway corridor, no longer takes access away, but a few metres that allow bikes do not make a long corridor a bike route either: without the half-length rule a 2.5 km corridor with 2 m of bicycle=designated, and the 1.9 km Bonterra Village Nature Trail boardwalk with a 10 m bicycle=yes footway, came out open to bikes. 1.1.0 required every member to allow a mode, so named trails change too: bike-allowed length is 3,291 km of named trails and 4,601 km in all, from 3,219 km and 4,498 km.
  - **Derived names.** A corridor of at least 100 m is named after a road ("Duck Road Path") only if one named road from the same extract runs within 40 m of it and within 30° of parallel for at least 60% of its length, so a road that crosses it never names it. Only paved shared-use paths qualify, because a plain footway beside a road is an untagged sidewalk and an unpaved path near one is a hiking trail (a forest trail was about to become "Blue Ridge Parkway Path"). A corridor that carries straight on (45° or less) out of a trail with a real name is that trail's unnamed end and gets no road name; 52 were withheld, such as a piece of Cross City Trail that would have been "Eastwood Road Path". Sidepaths on both sides of one road get the side in their name, "The Plaza Path (East Side)" and "(West Side)", because the app adds up same-named sections within 400 m and showed that road's path as 2.85 km (74 names). The side is on one compass axis per road, taken from the road's direction, and only rows on opposite sides are labelled. Judging each row by its own direction had labelled one piece "North Side" and the piece beside it "West Side". Two paths side by side on the same side of a road get no side (11 such pairs), so those still share a name. A road already called a path or trail gives "Sidepath" ("Virginia Dare Trail Sidepath"). Derived names carry `name_source: derived_road` in `tags_json`; the app does not read that yet and shows them like any other name.
  - **Sidewalks.** `highway=footway` + `footway=sidewalk` ways are dropped unless `--keep-sidewalks` is passed (then they are named "… Sidewalk"). The osmium recipe already removes all 144,858 of them, so this changes no rows today and guards inputs that skip that step.

### Fixed
- The "Goal" label on the Health tab's step charts (the week chart and "Last 30 Days") no longer sits on top of the "10K" axis label. - Position on a trail walk or a recorded route is tracked as a sequence of fixes, not decided one fix at a time. On 1,233 simulated walks each way round 411 real North Carolina loops, from random starting points with ±5 m GPS wobble:
  - backward walks that never finished went from 185 to 4
  - walks that said "Walk complete" before halfway went from 17 to 0 (the worst on the previous code finished 1% of the way round)
  - a change of mind, a restore, or walking home on the "wrong" side failed in 18 of 33 probes on the previous code, and 3 now

  **How it works.** Several guesses of where the person is stay alive at once. Each fix scores every guess by how far the fix is from the line there, and by whether getting there means travelling along the line about as far as the person actually moved. A step backwards costs 2 plus 0.18 a metre. On a loop the long way round is scored as well as the short one, but only once enough time has passed to walk it: a walk's first fixes near another stretch of a small loop were being credited with most of the loop. The cheapest guess wins, and one that loses a fix can win the next. Progress is the distance walked along the line, not the nearest point on it, so being beside a loop's finish is not having walked there.

  **Turning round.** The route turns round when the likeliest guess has been 25 m behind the start for two fixes in a row, and also 25 m behind where that guess's own walk began. The planner starts a trail at its nearest data point, which can be 100 m from the person. On the reversed route the checkpoints start over.

  **Known limits.** These are in the simulations, not reports from users:
  - a GPS gap of more than about 70% of a small loop still reads as walking back (381 of 411 loops are fine at 70%; the previous code managed 389)
  - 35 of 1,233 backward walks turn round more than 60 m later than they should
  - 18 finish early, never before 55% of the way
  - walking home 20 m from the return line of a recorded out-and-back counts backwards

  **The session's steps are shared.** The checkpoint step (`WaypointStep`, which also builds the "WP n/N" label) and turning round (`TrailProgress.turnedRound`) are functions that `NavigationSessionManager` and the tests both call. A restore passes when the walk was saved, so a person who walked on while the app was closed is not read as walking back.

The reminder fires at the chosen time with a Start Walk action, and asks for real alerts if delivery is only quiet — the user just asked for something. The 1.7 calendar integration wrote an `EKEvent` with a 10-minute alarm into the user's default calendar, which meant a Calendar permission prompt, a second app owning the reminder, and nothing Wockett could act on when it fired. Existing calendar events are left in place and still deletable from Settings under "Calendar Reminders" until none remain; `WalkSchedulerService` keeps only that. Duration is gone from the sheet — a notification has none. Adding the same route twice still keeps one reminder, at the later time; one-off reminders drop off the list once they have passed.
- In-walk notifications — water breaks, checkpoints, auto-pause, route events and the hydration nudge — are now delivered as Time Sensitive, so they break through a Focus mode. The user started the walk; a "drink now" or "you're off route" that waits until Focus ends is worthless. The streak nudge, pet nudge and route reminders stay at the normal level (that's Wockett interrupting, not the walk), and the weekly recap stays passive. The mapping is one exhaustive switch keyed on `NotificationKind`, so a future kind has to choose. Requires the entitlement from the previous change; without it iOS quietly delivers at the normal level.
- Time Sensitive Notifications entitlement added to the app target (`com.apple.developer.usernotifications.time-sensitive`). Added through Xcode's Signing & Capabilities with automatic signing, which also registers the capability on the App ID — adding the key to the plist by hand does not, and Xcode Cloud then fails to sign. No code sets `.timeSensitive` yet; the next notifications PR flips the in-session kinds (water breaks, checkpoints, auto-pause, route events) to it, and only those — it breaks through Focus, so it stays off the streak nudge and the weekly recap.
- Starting a guided session no longer shows the notification permission prompt. It asks for quiet delivery instead; the real prompt is reserved for moments the user asks for something — enabling water breaks, setting a route reminder, or a Settings toggle.
- Minimum iOS version lowered from 26.5 to 26.1. Nothing in the codebase required 26.5 — the highest floor any API actually imposes is `tabViewBottomAccessory(isEnabled:content:)`, which is iOS 26.1, and a build at 26.0 fails on that one call and nothing else. The previous value appears to have followed the installed SDK rather than a decision, and it excluded everyone on 26.1 through 26.4 who had not taken the latest point update. Previously a fresh route search filled the panel with a full-height weather card and one partially visible route card, putting the route list and Start Walk below the fold on the screen whose entire purpose is picking a route. Apple's required WeatherKit attribution stays visible in the collapsed state.

- SwiftData `@Model` properties all have default values (CloudKit compatibility requirement)
- AppModelContainer: four-tier fallback (CloudKit → local → wipe+retry → in-memory); no more `try!` on non-memory paths

- `print()` statements wrapped in `#if DEBUG` to keep production logs clean
